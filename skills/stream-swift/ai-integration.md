# Stream Swift - AI assistants, LLM chat, and agentic experiences

Use this runbook when the iOS request involves an **LLM or AI agent**: a ChatGPT-style app, an AI assistant / support bot / copilot in chat, streaming the model's answer, thinking indicators, "stop generating", rendering markdown / code from the model, showing the agent's reasoning and tool calls, asking the person before a tool runs (approvals), letting the agent run tools on the device, replies that are interactive UI (generative UI, A2UI, OpenUI), or showing what was said to a **voice agent** as a conversation.

Like the rest of this skill, it is a **router, not a copy of the docs**: it picks the pages to fetch, and adds only what the docs do not say. Fetch the pages live and apply them; cite what you used. **Read [`../stream/ai-backend-contract.md`](../stream/ai-backend-contract.md) first** - where the model runs, what the agent must send (including the `generating` flag iOS depends on, and the agent-steps format for reasoning / tool calls / approvals), and the CLI check are shared by every platform and live there.

The iOS AI docs live under `https://getstream.io/chat/docs/sdk/ios/ai-components` (index: `https://getstream.io/chat/docs/sdk/ios/ai-components.md`). The old `.../guides/ai-integrations/...` pages moved there, and their `.md` URLs return 404.

## Step 0: Which agent, which packages (decide before any code)

### The agent: Stream Agents, or one of your own

| The agent | The app uses | Read |
|---|---|---|
| **Stream Agents**: an `agents/<name>/` folder synced with `getstream agents`, run on Stream's router (any request that says Stream Agents, "agent folder", `getstream agents`, or builds a new agent with no backend of its own) | The `StreamAgents` Swift SDK to sign in, open sessions, ask, stop, approve and run device tools, plus `StreamChatAI` for the views. No backend agent to write. | `.../ai-components.md` (the quickstart builds exactly this), then `getstream docs agents` (`quickstart.md`, `sessions.md`, `generative-ui.md`) for the agent side; the stream skill covers the CLI |
| **An agent of your own** that writes into a Chat channel (Vercel AI SDK, LangChain, the Python Vision Agents SDK, a custom backend) | `StreamChat` + `StreamChatAI`, with a transport over the channel | `.../conversation-state.md` "A transport over a Stream Chat channel", and the shared contract |

When the request doesn't say, and nothing in the project shows a backend agent, take Stream Agents and say so.

### StreamAgents: install it like this

- Package `https://github.com/GetStream/Vision-Agents.git`, product `StreamAgents`, pinned to an **exact** version: `.package(url: "https://github.com/GetStream/Vision-Agents.git", exact: "0.3.0")` (in Xcode, the Dependency Rule "Exact Version"). Verified to resolve and build with Xcode 27.1 next to `stream-chat-swift` 5.16.0.
- **Never a range** (`from:`, up to next minor). The repository also carries the Python packages' `v` tags (`v0.1.0` ... `v0.6.9`), which SwiftPM reads as versions and which have no `Package.swift`, so a range resolves to one of them and fails with `the package manifest at '/Package.swift' cannot be accessed`. The Swift SDK's releases are the plain tags (`0.1.0`, `0.2.0`, `0.3.0`): list them with `git ls-remote --tags https://github.com/GetStream/Vision-Agents.git | grep -E 'refs/tags/[0-9]+\.[0-9]+\.[0-9]+$'` and pin the newest. The docs' `branch: "accelerate"` also works but moves under the app; `sdks/swift/README.md` still says to wait for a `v` tag from 0.7.0, which doesn't exist yet.
- `0.3.0` renamed the module from `VisionAgentsCore` to `StreamAgents`; the docs' code (`import StreamAgents`) needs 0.3.0 or later.
- The first resolve clones the whole monorepo (about 300 MB). Tell the developer it takes a while.
- It brings `StreamChat` and `StreamVideo`. Add `StreamChatAI` (and `StreamChatA2UI` / `StreamChatOpenUI` for generative UI) from `stream-chat-swift` yourself. Never import `StreamChat` and `StreamVideo` in the same file ([`RULES.md`](RULES.md) "Chat + Video name collisions").
- **Build on Stream's hosted router.** It is the default for every app on Stream Agents: `StreamAgents(apiKey:)` connects to it with the app's API key, and the router runs the agent and its models, so there is nothing else to deploy and no model keys to hold. The agent itself is a folder synced with `getstream agents sync <name>` (beta CLI, see the stream skill). For development, mint a token with the CLI (`getstream token <user_id> --ttl 2h`) and pass it as `agents.setUser(User(id: "<user_id>"), token: "<token>")`; in production, `setUser(_:token:)` takes a closure that fetches it from the developer's backend. The iOS quickstart (`.../ai-components.md`) builds exactly this.
- **The Vision-Agents sample apps are for reading, not running.** Take the view and session code of `examples/voice_agents/swift_assistant` and `swift_demo` into an app on the hosted router, but don't run them as they are or copy their setup (configure step, backend, router settings), and use `stream-chat-swift` 5.16.0 rather than the `develop` branch `swift_assistant` pins.

### Which StreamChatAI

**`StreamChatAI` ships in `stream-chat-swift` from 5.13.0** (GetStream/stream-chat-swift#4306), as a library product next to `StreamChat` and `StreamChatCommonUI`. Before that it was the standalone `stream-chat-swift-ai` package (last release 0.12.0), which is now the **fallback**. Both declare a target named `StreamChatAI`, so an app has one or the other, never both: SPM refuses the graph even when the app links only `StreamChat` from 5.13.0+ (`multiple packages ('stream-chat-swift', 'stream-chat-swift-ai') declare targets with a conflicting name: 'StreamChatAI'`).

**The latest release is 5.16.0** (2026-11-04, both Chat packages). It adds, to `StreamChatAI`: `AIConversation`, the state behind a conversation, reached through an `AIConversationTransport`, and shown by `AIConversationView(conversation:)` and `AIComposerView(conversation:)`; generative UI (`AIUIHost`, `AIConversationView(conversation:ui:)`) with the renderer libraries `StreamChatA2UI` (A2UI 1.0, iOS 15) and `StreamChatOpenUI` (OpenUI Lang 1.0, iOS 17); `AIClientToolDefinition.annotations` (`readOnlyHint`); and `AIComposerView` on iOS 15. **The docs are written for this shape**: the quickstart and every page build on `AIConversation` + a transport. 5.15.0 added `AIConversationView` (then driven by hand: `AIConversationView(messages:isThinking:...)`), `AIToolAuthorizationView` and the voice visualizations `AIVoiceGlowView` / `AIVoiceWaveView`, and embedded Splash and swift-markdown-ui instead of depending on their packages, so an app that imports `MarkdownUI` or `Splash` itself must add those packages directly when it updates past 5.15.0. `stream-chat-swiftui` 5.16.0 requires `stream-chat-swift` 5.16.0+.

Read the app's `Package.resolved` (or the project's package references), pick the row, and **tell the developer which version `StreamChatAI` needs for what they asked (5.13.0 for the components, 5.15.0 for `AIConversationView`, 5.16.0 for `AIConversation` and generative UI)** and which path you took:

| The app has | Do |
|---|---|
| no Chat yet | **Default.** Link `StreamChatAI` (+ `StreamChatA2UI` / `StreamChatOpenUI` when the agent writes UI) from `stream-chat-swift` `from: "5.16.0"`, and `StreamChat` unless `StreamAgents` brings it. Add `StreamChatSwiftUI` from `stream-chat-swiftui` `from: "5.16.0"` only for the message-list alternative (Step 1) or the SDK's channel list. |
| Chat 5.13.0 - 5.15.0 | Keep it for the components those releases have. When the app needs what is new in 5.16.0 (`AIConversation`, generative UI) or follows the current docs, **suggest raising both Chat packages to `from: "5.16.0"`**. Coming from below 5.15.0, check the `MarkdownUI` / `Splash` note above. |
| Chat 5.x below 5.13.0 | **Suggest the version update:** raise both Chat packages to `from: "5.16.0"` (Xcode: the package's Dependency Rule, then File > Packages > Update to Latest Package Versions). Per the changelogs, the source changes to check are `Device.createdAt`, now non-optional (5.13.0), and the `MarkdownUI` / `Splash` note (5.15.0). If the developer can't update now, take the fallback. |
| the standalone `stream-chat-swift-ai` | **Suggest migrating with the update:** remove the `stream-chat-swift-ai` package in the same change that raises Chat to 5.16.0 and link the `StreamChatAI` product of `stream-chat-swift` instead. The docs no longer carry a migration section; the 5.13.0 renames to apply are `AIAppearance` instead of per-view `colors:`, `isGenerating` on the composer view model, and `AIClientTool` + `AIClientToolRunner` instead of MCP `Tool` / `ClientTool` / `ClientToolRegistry`. If they'd rather not migrate yet, the app stays on the fallback. |
| Xcode 26 or older, no move to Xcode 27 | **Fallback.** Adding `StreamChatAI` from `stream-chat-swift` with SPM needs Xcode 27 (Xcode 26 rejects the target). |

**The fallback (standalone package).** Pin `stream-chat-swift-ai` to 0.12.0 and keep `stream-chat-swift` and `stream-chat-swiftui` below 5.13.0 (`.upToNextMinor(from: "5.12.0")`), or SPM rejects the graph. 0.12.0 is iOS 16+, depends on the MCP Swift SDK (swift-nio, swift-log, ...), and has the old API: `ComposerView(viewModel:colors:isGenerating:onMessageSend:onStopGenerating:)`, per-view `colors:` arguments, an `AIClientTool` with only `name` + `run`, and tools described with MCP `Tool` through `ClientTool` / `ClientToolRegistry`. It does have the parts, approval, client-tool runner and on-device model types. The docs no longer show its API, so take its signatures from that tag's `Sources/StreamChatAI`. Tell the developer the fallback is a stopgap and updating to 5.16.0 is the way forward. Stream Agents' `StreamAgents` needs `stream-chat-swift` 5.13.0+, so it can't be on the fallback.

**The docs are current through 5.16.0.** Where the docs and the code disagree, the source at the resolved version wins (`stream-chat-swift` `Sources/StreamChatAI`, `Sources/StreamChatA2UI`, `Sources/StreamChatOpenUI`; `Vision-Agents` `sdks/swift/core/Sources/StreamAgents`; the local SPM checkout, see [`docs-map.md`](docs-map.md) "When the docs fall short") - say so.

Decisions the docs leave to you:

- **Show the conversation with `AIConversationView`, driven by one `AIConversation`.** It is the primary way to show one person's conversation with an agent: shapes A, E and F, and C / D on top of A. Each question moves to the top while its reply writes out below it. Thinking, a message on its way, older messages, approvals, sign-ins, errors and reply actions are built in.
- **The alternative is the `StreamChatSwiftUI` message list with the AI components plugged in** (`/swiftui-integration.md`). Take it when the conversation needs what a messenger has and `AIConversationView` doesn't (reactions, threads, read state, several people in the channel), or when the app already shows that channel with `StreamChatSwiftUI` (shape B). In shape B, keep existing custom attachments and list modifiers when you add the AI ones - overriding the slot replaces the default (composite-slot trap in [`design-matching.md`](design-matching.md)).
- **Never a hand-built list** on the low-level client ([`custom-ui.md`](custom-ui.md)), for a typed chat or a voice agent's transcript (shape E). Tell the developer which of the two you used and why.
- **Install:** run [`setup.md`](setup.md) first (Chat v5; it also covers an empty folder), then add the packages from Step 0.
- **UIKit:** `StreamChatAI` is SwiftUI-only. Host its views with `UIHostingController`, or build the AI screen in SwiftUI.

## Step 2: Wire the components (what the docs leave out)

The docs show each component, the conversation, and the StreamChatSwiftUI wiring. These are the gaps found building working apps:

1. **The conversation (`AIConversation`, 5.16.0).** Keep one `AIConversation` per open conversation in `@StateObject`, and give the same object to `AIConversationView(conversation:)` and `AIComposerView(conversation:)` (below the list, or over it with `safeAreaInset(edge: .bottom)`). It shows the sent message at once, the thinking state, the stop button, errors, older messages, edit and regenerate. Its transport is the docs' `AgentTransport` on Stream Agents (quickstart Step 4: `session.chat()` for the channel, `await session.start()` before asking, `session.responses.create`, `session.interrupt()`), or the docs' channel transport for an agent of your own (`/conversation-state.md`). Make the transport asynchronously before the view (the quickstart's `AssistantScreen` does it in `.task`), since `session.chat()` is `async throws`. This path needs no `StreamChatSwiftUI`: no `StreamChat` wrapper object and no `ViewFactory`. Theme it with `AIAppearance`, and change rows through `AIConversationViewFactory`. On 5.15.0 (no `AIConversation`), the view is driven by hand, `AIConversationView(messages:isThinking:...)` with a separately wired `AIComposerView`: suggest 5.16.0 rather than building that.
2. **The message-list alternative.** Conform to `MessageTypeResolving` as the SwiftUI integration page does - `MessageTypeResolver` is `public`, not `open`, so it can't be subclassed. The `makeCustomAttachmentViewType(options:)` slot renders bare (no bubble), so the reply is full width. For an AI-first app on this path, set `MessageListConfig(shouldMessagesStartAtTheTop: true)` so a new conversation reads from the top like a document instead of hugging the composer; `MessageListView` applies it itself and still anchors to the newest message once the list fills the screen.
3. **Approvals.** Pass an `AIToolApprover` as `AIConversation(transport:approver:)`. On Stream Agents its `decide` closure is `session.decide(call.id, allowed:)` (the quickstart's `approver`). With an agent of your own, hold one approver per signed-in user and install, and have it post `{tool_call_id, client_id, allowed}` to an authenticated backend endpoint, which checks the caller and updates the step (on the message-list path, the view factory is a good owner).
4. **Device tools.** On Stream Agents, give the session its tools (`agents.chat(agent:tools:)` with `AgentTool`s, `executor: .client`) and `start()` the session before asking: its socket runs them. With an agent of your own: the registration has no display title or approval spec, so if the backend should ask before a device tool runs, send those alongside (an `Encodable` wrapper that encodes the SDK registration and then its own keys into the same keyed container); hand `runner.run(parts)` every agent `MessageNewEvent` / `MessageUpdatedEvent` (a `chatClient.eventsController()` delegate) as well as the replies already loaded when the conversation opens - a view alone runs only while the reply is on screen. Either way, request OS permissions inside the tool.
5. **Stop.** With `AIConversation`, the composer's stop button calls the transport's `stop()`: `session.interrupt()` on Stream Agents. On the message-list path, set `composerViewModel.isGenerating` from the indicator events as the docs show, and send `AIIndicatorStopEvent(cid:)` through a channel events controller (the client-wide `EventsController` has no `sendEvent`), keeping that controller alive until the completion fires.
6. **Session.** If the backend issues expiring tokens, connect with `connectUser(userInfo:tokenProvider:)`: `connectUser(userInfo:token:)` rejects a token that has an expiry. On Stream Agents, `agents.setUser(_:token:)` with a closure asks again after a 401; `agents.use(chatClient)` / `agents.use(streamVideo)` hand over clients the app already has.

The reference app (`https://raw.githubusercontent.com/GetStream/chat-ai-samples/main/ios/AIComponents/<file>`: `AIComponentsApp.swift` init + message resolver, `AIComponentsFactory.swift`, `TypingIndicatorHandler.swift`, `AgentService.swift`, `ContentView.swift`) shows the message-list path. It still imports `MCP` and the standalone package: apply the 5.13.0 renames from Step 0 when you copy from it.

## Step 3: State the contract, leave a tripwire

State the backend contract from [`../stream/ai-backend-contract.md`](../stream/ai-backend-contract.md) to the developer - on iOS both `ai_generated` and `generating` are required, and the agent-steps attachments are what the parts views render - and run its CLI check before debugging Swift code. On Stream Agents the router writes all of it, so a missing field there is a router problem to report, not app code to add. Then leave a debug-only tripwire where messages are mapped (your `AIMessage` type, or the message resolver on the message-list path), so a missing field shows in the Xcode console. On the message-list path a missing `ai_generated` is a silent plain bubble; the docs' `AgentMessage` takes the role from `ai_generated`, so there it draws the agent's reply as the person's (match your agent's user id):

```swift
#if DEBUG
if message.extraData["ai_generated"]?.boolValue != true, message.author.id == agentUserID {
    print("[AI] Agent message \(message.id) has no `ai_generated: true` - the backend agent must set it.")
}
#endif
```

## Generative UI (shape F)

The agent writes a reply's UI (A2UI or OpenUI), the router moves it into the message's `ai_ui` custom field, and `AIConversationView(conversation:ui:)` shows it in place of the text. Fetch `/generative-ui.md` (and the Agents `generative-ui.md` on Stream Agents). What they leave out:

- **Packages:** 5.16.0, plus `StreamChatA2UI` (iOS 15) and/or `StreamChatOpenUI` (iOS 17). With a deployment target below 17, make a host with `OpenUIRenderer` only on iOS 17 and later.
- **One `AIUIHost` per conversation**, kept as long as the conversation shows (next to its `AIConversation`), so a form keeps what the person typed. Your `AIMessage` returns `uiDocument` (`AIUIDocument(customData: message.extraData)`), or no reply shows UI.
- **On Stream Agents, the host's `send` asks the session**: `try await session.responses.create(action.label, uiAction: action.json)`. The iOS page's `chat.sendMessage(...)` is for an agent of your own; the router doesn't answer a message sent to the session's channel. Catch the error in `send` to tell the person asking failed.
- **Tell the agent what the app shows.** The model only writes UI the agent's `instructions.md` describes. On Stream Agents the instructions are files synced with the CLI, so the app can't hand over `ui.capabilities` at runtime. Generate them from the same components with the public API, in a unit test that runs on the simulator (it writes to the Mac's disk, so the file lands in the repository): build the app's `AIUIHost` (or call `A2UIRenderer(...).capabilities(components:tools:)`), join each renderer's `instructions` from `ui.capabilities["renderers"]`, write them next to the agent's folder via `URL(fileURLWithPath: #filePath)`, then merge them into `instructions.md` and run `getstream agents sync <name>`. Re-run it whenever a component changes. The test file needs `import StreamChatA2UI` / `import StreamChatOpenUI` itself (member import visibility). A2UI lists an app component in PascalCase (`place_card` becomes `PlaceCard`), so write the renderer's `instructions` with that name. The iOS generative UI page shows the test. Don't copy the `swift_assistant` sample's `prompts/generate.sh`: it compiles the SDK's non-public prompt builder into a throwaway package, which only its example checking and catalog trimming need.
- **No generative UI on a call.** While voice is on, a typed turn isn't marked finished and the next `responses.create` is refused, and a tap in a reply's UI is a `responses.create` too. So while the call is up: no composer, show the transcript without the host (`AIConversationView(conversation:)`, so each reply shows its words), and say in `instructions.md` that the agent answers in words, not UI, on a call. Pass the host again once the session is back in writing. `leave()` ends a session that `VoiceSession.start` opened, so a voice mode inside a typed chat joins with `VoiceSession.attach(agents:sessionID:)` after `session.startVoice()`, and calls `session.stopVoice()` after `leave()` (`sessions.md` "Voice UI").

## Shape E: a voice agent

The person talks to an agent on a call, and the app shows the agent's state (a glow or a wave) and what was said, during the call or after it. Left alone, the transcript becomes a hand-built `ScrollView` of bubbles (the closed-captions docs page shows one). Use **`AIConversationView`** instead. It shows the person's lines as bubbles and the agent's as streamed Markdown, with a thinking state, a scroll-to-latest button and loading of older lines, and it takes any `AIMessage` (`id`, `role`, `text`, `isGenerating`).

**Check the fit first**, and tell the developer which way you went:

| The request | Use |
|---|---|
| One person and one agent, shown as a running conversation | **`AIConversationView`** |
| Subtitles over the call: a line or two that follow the voice and fade | A caption band from the closed-captions page. This is not a conversation, and the agent's text arrives ahead of its voice |
| A meeting with several people, with or without an agent | Not this view: it starts a turn at each of the person's messages and draws every other role as the agent. Use a custom list, or the `StreamChatSwiftUI` message list when the transcript is in a Chat channel |
| People and a bot chatting in the same channels | Shape B |

### On Stream Agents (`VoiceSession`)

Fetch `/use-cases/voice-agent.md` and `sessions.md` "Voice" (`getstream docs agents`). `VoiceSession.start(agents:agent:)` starts the agent on a call, `await voice.session.start()` follows it, and `await voice.join()` joins from the phone (it doesn't throw; a failure is in `voice.failure`). The transcript is the session's own conversation: `voice.session.turns` mapped to an `AIMessage` (the use case's `TurnMessage`), or `session.chat()`'s channel through the quickstart's `AgentTransport` and an `AIConversation` (the sessions page's `VoiceScreen`), which also keeps it as history. Drive `AIVoiceGlowView` / `AIVoiceWaveView` from the call (who is speaking) and `session.state`, as the docs do. The router keeps the session's channel and the SDK opens it, and joins the call, as the user `setUser` named, so none of the channel-id, membership, chunk-joining or captions advice below applies. No composer and no generative UI while voice is on (see "Generative UI"). `StreamVideo` comes with `StreamAgents`; add a microphone usage description.

### With a voice agent of your own

The agent is the Python Vision Agents SDK, OpenAI Realtime, or the developer's own, on a Stream Video call. Map each source to one `AIMessage` type:

- **A Chat channel the agent writes.** The Python Vision Agents SDK keeps the conversation in a Chat channel whose id is the call's id: `messaging:<call id>` in the released 0.6.x. It posts the person's words as their messages and the agent's as the agent user's, streamed with `generating` (ephemeral updates, then a final partial update). Watch the channel with a `ChatChannelController` (synchronize it first) and wrap its messages as the docs' `ChatAIMessage` does (`/conversation-view.md`, "Messages from Stream Chat"). A few things are specific to a transcript:
  - `role`: keep the docs' `isSentByCurrentUser` rule. Don't key on `ai_generated` or `source` here: the released Python SDK doesn't set `ai_generated`, and the Go agent sets `source: "agent"` on every message, the person's included.
  - Long text: the Python edge splits anything over 1000 characters into several messages that share `extraData["chunk_group"]`, ordered by `chunk_index`. Join them into one.
  - Paging: pass `loadOlderMessages` (from `loadPreviousMessages`) while `!hasLoadedAllPreviousMessages`.
  - Membership: the person must be a member of the channel, or reading it fails with a permission error. The released Python SDK adds nobody outside `open_demo`, so with it the backend must add the person once the agent has created the channel (`channel.update(add_members=...)`). If the backend can't be changed, take the captions path instead, and tell the developer why.
- **Closed captions** (no Chat needed). `call.state.closedCaptions` keeps only the latest two, for about 2.7 s: fine for subtitles, lossy for a transcript. Instead, consume `call.subscribe(for: ClosedCaptionEvent.self)` for as long as the call runs, and append each event's `closedCaption`. A caption from the person's own user id (`closedCaption.user.id`) is `.user` and any other is `.assistant`, and consecutive captions from the same speaker join into one message. Captions must be on for the call type (`auto-on`, or `call.startClosedCaptions()` with the permission; see the closed-captions page). They arrive as finished segments, so the agent's lines show whole rather than typed out.
- **The agent framework's own events**, such as a client SDK that hands over transcript turns, or custom call events. Map its turns the same way: who spoke, the text, and whether it is still being written.

**Wiring:**

1. Build an oldest-first array of one `AIMessage` type: the docs' `ChatAIMessage` for a Chat channel (the controller lists newest first, so reverse it), or a small type of your own for captions (`struct TranscriptLine: AIMessage { let id: String; let role: AIMessageRole; var text: String; var isGenerating = false }`). Keep each line's id stable across updates (a message id, or the speaker plus the first caption's start time): a changing id rebuilds the row and loses the scroll position.
2. A transcript with no requests to send is the one place to drive the view by hand: `AIConversationView(messages: lines, isThinking: ..., emptyContent: { ... })`. `isThinking` is optional. Set it from the agent's state when the app has one (from the person's last words until the agent's line appears). The view already shows thinking while the latest reply is `isGenerating` with no text. If the person can also type to the agent, use an `AIConversation` with a transport instead, as in Step 2.
3. Put the call controls (mute, hang up, the voice visualization) below the list, or over it with `safeAreaInset(edge: .bottom)` so the list knows how much of it is covered.
4. Packages: `StreamChatAI` depends only on `StreamCore`, so for the captions path a Video-only app adds just that product from `stream-chat-swift`. The Chat-channel path also needs `StreamChat`. Keep the `ChatMessage` mapping in a file that imports `StreamChat` + `StreamChatAI`, and the call screen in one that imports `StreamVideo` (+ `StreamChatAI`). Never import `StreamChat` and `StreamVideo` in the same file ([`RULES.md`](RULES.md) "Chat + Video name collisions").

## Pitfalls the docs do not shout about

- **A channel the backend created must be synchronized before the first message.** `createNewMessage` on a fresh `ChatChannelController` for a channel that isn't in the local DB yet is dropped; `synchronize()` it first (wrap the completion in a continuation - there is no async variant), and pass a completion to `createNewMessage` to surface errors.
- **"Conversations with the agent" needs two member filters.** `.containMembers(userIds: [me, agent])` is `members $in [...]` - it matches channels with *either* member and leaks other people's conversations with the agent. Use `.and([.containMembers(userIds: [me]), .containMembers(userIds: [agent])])`. On Stream Agents, list conversations with `sessions.query` instead (`sessions.md`).
- **`ChannelType(rawValue:)` is internal.** Map a channel type string from the backend to `.messaging` / `.team` / ... / `.custom(value)` yourself.
- **If you clear the composer yourself** (a custom input slot), use `clearAfterSending()`, not `cleanUpData()`: `cleanUpData()` deletes the photos the composer took, which the sent message uploads later.
- **Xcode 27 app templates turn on `MemberImportVisibility`** (and default MainActor isolation): a file using `localizedDescription` or a `CGFloat` literal needs `import Foundation` even when Stream modules are imported, and a file using `A2UIRenderer` needs `import StreamChatA2UI` even when another file of the target imports it.
- **Info.plist:** the composer's speech and photo / camera inputs, and a voice call, crash on first use without the usage descriptions the docs list (`NSMicrophoneUsageDescription`, `NSSpeechRecognitionUsageDescription`, `NSCameraUsageDescription`, `NSPhotoLibraryUsageDescription`); a location device tool also needs `NSLocationWhenInUseUsageDescription`.
- **Local backend:** the simulator reaches `localhost`, a physical device does not (use the Mac's LAN IP or a tunnel). Keep the base URL in config. For a location tool in the simulator, set one (`xcrun simctl location booted set <lat>,<lon>`).
