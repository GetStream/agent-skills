# Skill eval plan

The only real test of a skill is running prompts with it. The harness (`run.py`) runs a
prompt through `claude -p` in an isolated sandbox with a chosen set of skills installed,
grades the outcome, and reports.

The first two attempts (2026-08-26/27) were invalidated by harness defects discovered mid-run:
the control could read the repo's own skills, then the CLI-installed v1 skills; snapshot
copies of two rotating credentials went stale; runs were truncated by turn budgets and
killed by OOM; skills were edited while runs were in flight. Nothing from those runs is
kept. This plan restarts in three stages, each gated on the previous one behaving exactly
as predicted.

## Configurations

- **A** = v1 skills (git tag `v1-skills`), **B** = v2 skills (`v2/` plus the v1 platform
  packs), **C** = control: no skills installed and none reachable.
- Skills are invoked explicitly: A and B send `/<skill> <prompt>`; C sends the bare prompt.
  Auto-invocation is not the product.
- Skill text is frozen for the duration of a run. Edits between runs are fine; edits during
  one invalidate it.

## Stage 1 - harness self-test (one case, synthetic skill)

A skill whose only content is a fact, in two versions, so every configuration has one
unambiguous correct answer:

- A: `test-skill` says "the magic word is ooglygoo"
- B: `test-skill` says "the magic word is pitted olives"
- C: no skill
- Prompt: `/test-skill what's the magic word?` (C: `what's the magic word?`)

Expected: A answers ooglygoo, B answers pitted olives, C says it does not know (or asks).
Graders: a regex per expected answer, plus the same criterion as an LLM judge (Opus 5), so the judge
is validated against a deterministic truth. Also checked: C's transcript touches no
`SKILL.md`, `/skills/`, or `peers.yaml` path (control integrity, scored in C only);
`--regrade` reproduces the verdicts without agent calls.

Pass condition: all three configurations produce the predicted answer and both grader
kinds agree, three runs each. Anything else is a harness bug, fixed before stage 2.

## Stage 2 - one case per category, A/B/C

- Routing: "how does useCreateChatClient work?" (docs read; answer correct; no WebFetch).
- Existing app: "add UI for managing channel members" on the `chat-app` fixture (build
  passes; no invented API; docs read before the first edit).
- New app: "build me a Slack-like team chat app" (build passes; no invented API; login
  screen first; secret only server-side; `getstream env` used).

Pass condition for the *harness*: every run completes without truncation or environment
error, the control stays clean, and each grader's verdict matches a human read of the
transcript. Skill results are recorded but not yet interpreted.

## Stage 3 - full suite

All cases, A/B/C, one configuration at a time (serial - OOM). Report generated by
`compare.py`, judged findings written by hand into `reports/`, cumulative log in
`FINDINGS.md`.

## Environment rules (learned the hard way)

- Workspaces outside the repo, on the home disk (`~/.cache/stream-evals`), not tmpfs.
- Per-run HOME containing only: the CLI account auth when the case needs it (rotating -
  copied in at start, carried back at end, under a lock), `config.yaml`, and a symlink to
  `~/.stream/docs`. Never `~/.stream/skills/`.
- Claude credentials symlinked, never copied (rotating).
- Agent runs in its own process group, killed at run end (dev servers).
- One suite at a time; browser-spawning cases never concurrent with anything.
- Keep the laptop awake during runs (OAuth expiry on sleep kills the run in flight).
- The eval test account: a dedicated Stream account, separate from the operator's daily
  login; app `stream-evals`; apps created by tests are kept.
